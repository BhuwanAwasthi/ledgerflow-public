# Decisions and assumptions log

Claude appends here when the spec is silent or a phase defers something. State these in the demo.

- PS-1 chosen; vendor onboarding (PS-2) is a light mini-flow inside one edge case.
- No ERP posting: the approved ERP import file (single or batch) stands in for posting.
- No outbound email API: vendor/submitter messages are drafts with mailto links; missing documents arrive via a no-login vendor portal link.
- Demo has no real auth: a role switcher (Submitter / AP Reviewer / Admin).
- 2-way match by default; GRN quantity check when a GRN exists.
- Tolerance: unit price must exceed both 2% and $50 per unit to fail; PO balance tolerance 2%.
- Implied PO matches never auto-approve.
- Seeded dashboard history is labelled as seeded demo data in the UI.

## Phase B1
- Case status enum adds `unsupported`: workflow.yaml ends at `end:unsupported` (no invoice found) but SPEC §6 omitted it. Allowed terminal targets: approved, rejected, unsupported, failed.
- `workflow.yaml options.sticky_review_redirect: {auto_approve: template_draft}` names where sticky review sends an auto-approve once a reviewer has acted, so the stage id is not hard-coded. "Has been reviewed" = at least one review_action row exists.
- Pause statuses: a `hitl` stage sets the case to `needs_review`; a `wait_for` stage sets it to `on_hold` (with `sla_due_at` from `app.sla_hours`).
- Each case runs on the config snapshot taken at creation (hash + full files in `cases.config_snapshot`); later Agent Studio edits apply to new cases (and to reruns, once rerun exists).
- Case state is not a column: it is folded from completed/waiting stage_event outputs per agent id (append-only, replayable).
- `run_no` increments on every resume (review action, event, startup restart); stage_events `seq` is per case.
- Added `cases.note` (upload form note; not in SPEC §6) and `app.yaml limits.max_stages_per_run` (loop guard).
- Agents whose handler module does not exist yet run as `StubAgent`; `FORCE_STUB_AGENTS=true` forces stubs everywhere. Tests always force stubs and script outcomes per stage (`!error` / `!sleep:s` to test retries and timeouts).
- Sync SQLAlchemy sessions are used inside async routes and the orchestrator (queries are tiny; concurrency is 2). Revisit if Postgres latency on Render shows up in the live view.
- `make check` skips the frontend typecheck/build while `frontend/package.json` does not exist (F1 creates it); it uses make's `$(wildcard)` so it is shell-agnostic.
- SSE: `GET /api/cases/{id}/events/stream` replays stored events (honours `Last-Event-ID`), then streams live `stage_event`, `case_updated` and `progress` events; `?follow=false` closes after the replay.
- Accepting a review action or a `wait_for` event writes the paused stage's `completed` event and moves `current_stage` to the next target before the job is queued, so a restart (Render sleeps often) continues from there instead of losing the action.
- An orchestrator-level crash (loop guard, DB error) still appends a `failed` stage_event with the error text.
- Deferred: a review POST that arrives while the same case is mid-run waits for the per-case lock before getting its 409. That's harmless with stubs; revisit in B2 when LLM stages take seconds.

## Phase D1
- scenarios.yaml gained print-only realism data the spec left open: vendor `address` and `bank_name` (incl. the S05 new vendor), PO `created_at` / `approved_by` (needed by the 20% date-window score), GRN `received_at`. Totals and IDs are unchanged.

- `make fixtures` runs `python -m scripts.generate_fixtures` from backend/ (so `app` imports without sys.path hacks). Output is byte-deterministic (reportlab invariant mode, seeded scan noise); a test regenerates into tmp and fails if committed fixtures are stale (scan JPEG bytes excluded, as they can differ across Pillow builds).
- Four layout families (classic, banner, ledger/Courier, sidebar) styled per vendor with different labels, date formats ("Oct 02, 2026", "2026-10-05", "08 Oct 2026", "October 01, 2026") and money formats ("$1,250.00" vs "1,250.00 USD"). Dates are always unambiguous (no 10/02/2026). Every PDF carries a tiny "synthetic test document, fictional companies" footer.
- LLM output schemas live in `app/llm_schemas.py` (InvoiceExtraction, ChangeSet, plus ClassifierOutput, POInferenceOutput, GLCodingOutput, DecisionExplanation, CommsDraft). Strict-mode shaped: `confidence` and `location` are fixed-key objects (strict mode forbids free-form maps); `location` covers the 7 header fields the prompt names. Money is `Decimal` in Python and `number` in the JSON schema. B2's llm.py should reuse these.
- FakeLLM fixture format (`tests/llm_fixtures/<scenario>__<agent>.json`): `{scenario, agent, documents, calls: [{action, schema, when, output}]}`. A call matches when all its `when` keys equal the caller's context (`document`, `pages`, `invoice_number`, `decision`, `remark`); empty `when` = default. Only LLM-calling actions have fixtures: classify (incl. the S05 W-9 and bank letter), extract, po_matching.match (explicit PO = 1 candidate for line pairing; no PO = all the vendor's open POs; none when the vendor has no POs), suggest_gl (S05, S07), decide, apply_remark (S02b), comms drafts (S04 rejection; S05/S06/S09 requests).
- Expected extraction confidences: clean 0.95-0.99; scans ≤ 0.8 (the prompt's rule), so a scan can never pass the 0.90 auto-approve gate. A field that is absent gets `null` confidence and `null` location (not 0).
- Comms fixture bodies say "through the secure link below" instead of containing a URL: the portal token only exists at run time, so the comms agent appends the link.
- Seeded history (40 cases over 21 days, deterministic RNG, dates relative to "now"): final status approved (or rejected for reject decisions) so it never fills the work queue; a completed stage_event per happy-path stage up to `decide` (path walked from workflow.yaml, LLM stages carry token metrics, cost from app.yaml pricing); one or two failed rule_results chosen from rules.yaml by the severity matching the decision. No PO consumption, so demo balances start exactly as in scenarios.yaml.
- Fixture cases are submitted as the vendor's billing contact (`billing@<domain>`), or the buyer's AP mailbox for the two-vendor S10 bundle. Supporting files (S05 W-9, bank letter) are downloadable from `GET /api/fixtures/{id}/files/{filename}` for the vendor-portal demo step; they are not attached to the case.
- Notes for B2/B3 from the D1 spec review: (1) `ChangeSet.ops` produces `oneOf` + `discriminator`; llm.py must rewrite to `anyOf` and drop `discriminator` for strict mode. (2) FakeLLM `when` values are exact: the S02b reconciler fixture keys on scenarios.yaml `demo_remark` verbatim; S10 keys on the extracted (not normalised) invoice number; S10 child cases must not re-classify by the parent filename. FakeLLM should fall back to the scenario file's first call for an action when nothing matches. ## Phase B2
- Bundles: the classifier gains outcome `split` -> `end:split` (new terminal case status `split`; F-phases need a colour for it in `status.ts`). Each invoice in the upload becomes a child case (`parent_case_id`, same submitter, source and config snapshot) and is queued by the orchestrator through the new `AgentResult.spawn` list. A child's document row points at the parent's stored file with `page_from`/`page_to` and the label already set, so the child skips the classifier LLM call (FakeLLM `when.pages` keys on original page numbers, and bbox pages stay those of the original file). The same rule applies to any upload with more than one invoice, including several single-invoice files.
- One file holding several documents (e.g. an invoice plus a delivery note) keeps one `documents` row per page-range segment (same `storage_key`, no bytes copied).
- Page renders and text layers are content-addressed in storage: `renders/<sha256>/pages/<n>.png` and `renders/<sha256>/text.json`, so segments and child cases share them. The future `/documents/{doc_id}/pages/{n}.png` route resolves via `documents.sha256`.
- Intake: a file whose format is not PDF, image or DOCX is skipped with a reasoning line; if nothing usable is left the outcome is `empty`. More pages than the limit is `too_large`. DOCX is converted text-only (PyMuPDF cannot open DOCX, and there is no LibreOffice on Render free). "Scanned" means fewer than `intake.params.min_text_chars` characters in the text layer.
- Classifier: the label enum is injected into the strict schema from document_types.yaml. A label below `min_confidence` becomes `other` (the model's label and confidence stay in the reasoning). Images of the first `pages_per_document` pages plus the text layer of every page (truncated to `max_text_chars`) are sent, so a long bundle is still split correctly.
- Extraction: the outcome is `failed` only when there is no invoice number, no total and no lines; it is `low_confidence` when any configured `confidence_fields` value is below `low_confidence_below`. `cases.confidence` = the minimum of those header confidences. Exact bboxes: each located value is searched in the text layer (amounts with and without thousands separators; ISO dates re-printed in `locate_date_formats`). Among several hits, the one closest to the model's box wins. Values that wrap across lines (e.g. a two-line vendor name) fall back to the model's box, marked `source: model`.
- Vendor memory before the vendor check: the vendor is "known" from the vendor stage (a re-extraction), else the submitter's email domain, else a master legal name printed in the text layer.
- Normaliser: amounts are emitted as decimal strings (exact in JSON). Its output (`state.normaliser.invoice`) is the canonical invoice for B3; `extractions` keeps the model's raw output. Missing line amounts are computed from qty x unit price, and a subtotal+tax+shipping vs total mismatch becomes a warning plus `arithmetic_ok: false` (the rule decides in B3). Ambiguous numeric dates follow `date_formats_hint` order and are flagged.
- LLM adapter: `api_path: auto` is resolved by a background probe at startup (a tiny strict-schema Responses call, then a Chat call); `/healthz` shows `responses|chat|unavailable|not_probed`. The strict-schema post-processor also drops `minimum/maximum/format/default/title` and rewrites `const` to `enum` (Pydantic validates bounds after parsing). Cached responses report 0 tokens and cost with `cache_hit: true`. An agent YAML without `model.max_output_tokens` is an error, not a silent default.
- `LLM_BACKEND=fake` serves the recorded FakeLLM fixtures from the running app (frontend work offline); default is `azure`.
- Fixed B1's deferred item: a review POST on a case that is not `needs_review` now returns 409 at once instead of waiting for the per-case lock while an LLM stage runs.
- Live run (gpt-5.2, Responses path): header-field accuracy 36/36 on S01, S04, S08, S09. Extraction takes 25-41 s per call at medium effort; classification takes 3-10 s. Cost shows $0 until `llm.pricing_per_1m_usd` in app.yaml is filled in.
- `make test-live -k extraction` would hand `-k` to make (keep-going), so the Makefile passes `ARGS`: `make test-live ARGS="-k extraction -s"` prints the table.
- Spec review fixes: re-running the classifier on an already split bundle (a restart before the stage event was written) reuses the existing child cases and queues nothing new. One-word values are located only as whole words (`$100.00` is matched, but `100.00` is not found inside `1,100.00`, nor `8.25` inside `8.25%`). Numeric date formats moved to `normaliser.params.date_numeric_formats`.
- Deferred from the B2 review:
  - A real invoice the classifier labels below `min_confidence` becomes `other`, so the case ends `unsupported` with the reason in the reasoning lines. A "low-confidence document → review" route needs a workflow outcome and a UI state; revisit in P6 if live classification ever drops below 0.70 (live runs were 0.95+).
  - Pages no classified range covers are dropped without a reasoning line.
  - `normaliser.arithmetic_ok` is an exact cent check for display only; B3 rules must apply the rules.yaml tolerance.

## Phase B3
- Duplicate detection needs the invoice number per case, so `cases` gains `invoice_number` (as printed), `invoice_number_norm` (indexed) and `invoice_date`, set by the normaliser and exposed on `CaseOut`. No Alembic: run `make seed` to recreate a dev DB.
- Duplicate candidates are other cases of the same vendor that are not seeded and not `failed/unsupported/split/rejected`. `duplicate_near` compares invoice dates (else created dates) within `window_days`; an invoice with no number counts as a different number (S09 is flagged as a possible duplicate of S10's CL-781: same vendor, same 1,250.00, no number).
- Rule scope: `applies_to: po` rules run when a PO is linked **or** a PO number is printed (so `po_valid` can explain a bad reference); rules that need PO data (price, GRN, balance, lines, currency) are then "not applicable" without a linked PO. `non_po` rules run when no PO is linked. Not-applicable rules are listed in the policy output (`not_applicable`), not stored as rule_results.
- Rule statuses: `fail`; `warn` for an info-severity failure or a reviewer override (explanation "Overridden by reviewer: <reason> (was: …)"); `pass` (explanation "<rule name>: OK."). Multi-item rules (price, GRN) render `explain` once per offending line and join them.
- Boundaries are strict "greater than": exactly at a tolerance passes. `price_tolerance` only flags over-billing. `po_balance` compares the invoice **subtotal** (pre-tax, as the S02b numbers require) with remaining = (PO amount, or the reviewer's amendment for this case) - reserved/consumed by other cases; with nothing left any amount fails ("over by 100+%"). `quantity_vs_grn` compares with GRN received minus qty already invoiced against that PO line by other cases, and only for PO lines that have a GRN. `tax_rate_valid` uses printed line rates when present, else accepts any allowed rate within `rounding_tolerance` (new param, 0.01) of tax_total.
- Date rules use today's date via `app.agents.policy.today()` (tests pin it to 2026-10-11).
- Reconciler contract for B4: policy reads `state.reconciler.rule_overrides {rule_id: reason}` and `state.reconciler.po_amendments {po_number: amount}`.
- Decision outcomes come from `decision.yaml params` (`severity_outcomes`, `pass_outcome`, `gate_failure_outcome`). The `min_extraction_confidence` gate checks the `required_fields` rule's fields; a missing confidence fails the gate. `require_explicit_po` means non-PO and implied invoices never auto-approve.
- Reservation: at `decide`, for outcomes in `reserve_po_balance_on`, the case's earlier reservation is released and one row per invoice line is reserved (lines not on the PO count against the PO header). Right before reserving, `po_balance` is re-run against the live ledger with no `await` in between; if it now fails, an auto-approve becomes needs_review. On hold / reject release the case's reservation. Consumption on approval (`po_ledger.consume`) is called by `finalize` in B4, so after B3 S01 shows PO-1002 4,415.00 *reserved*, not yet consumed.
- The decision explanation LLM call gets only the rule results and gate failures; if it fails, the summary is built from the failing rules' explanations (reasoning line says so) and the stage still completes.
- Vendor check: `pending_docs` vendors route to `new_vendor` (onboarding reuses the open request); `inactive`/`rejected` to `inactive_vendor`. IBANs are compared as sha256 of the upper-case alphanumeric IBAN. `request_onboarding` creates the vendor row (`pending_docs`, next `Vnnn` code, details from the invoice) plus a vendor_request with a random token; the output carries `portal_path` `/portal/<token>`, and comms/UI prefix `PUBLIC_APP_URL`.
- PO inference: amount closeness = 1 - |subtotal - remaining| / max(both); date score = 1 when the invoice is dated 0..`date_window_days` after the PO, else 0; line similarity from the LLM. For an explicit PO the LLM is still called once (one candidate) for line pairing. Model-proposed pairs are validated in code (PO line must exist, used once). An explicit reference that is missing/closed/another vendor's is recorded as `explicit_issue` and the vendor's open POs are scored instead.
- suggest_gl only accepts codes from `gl_accounts`; unknown suggestions fall back to the vendor's default GL (noted in reasoning). History = the primary GL of the vendor's last 5 approved non-PO cases.
- Scenario test asserts `failed_rules` as a subset (as D1 noted); S05's `after_onboarding` simulates the admin approval directly (vendor status + `fire_event(vendor_approved)`) until B4 builds the portal/approve endpoints.
- Spec-review fixes: a late `po_balance` failure at reservation time also rewrites that rule's stored result and feeds the explanation, so the Rules tab and the summary agree with the decision. The reservation equals the subtotal that `po_balance` checks (a gap between the subtotal and the line amounts is reserved on the PO header). Duplicate candidates are only *earlier* cases, so two copies processed concurrently don't reject each other. Model-proposed line pairs also need a rapidfuzz description floor (`po_matching.params.pair_min_similarity`, 50). Severity ordering in reasoning follows `decision_precedence`; the GL history size is `gl_history_cases`.
- Deferred to B4: (1) a case that fails after `decide` (e.g. at the template stage) keeps its reservation; B4 should release it on `end:failed` / rejection along with `consume` on finalize. (2) `po_ledger.balance()` (PO screen) shows the master amount; a reviewer's per-case `po_amendments` raises the amount only for that case's rule, so the PO screen can show a negative remaining (PO-1001 -300.00 after S02b until the amendment is applied in B4).
