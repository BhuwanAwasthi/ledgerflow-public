# Decisions and assumptions log

Claude appends here when the spec is silent or a phase defers something. State these in the demo.

- PS-1 chosen; vendor onboarding (PS-2) is a light mini-flow inside one edge case.
- No ERP posting: the approved ERP import file (single or batch) stands in for posting.
- No outbound email API: vendor/submitter messages are drafts with mailto links; missing documents arrive via a no-login vendor portal link.
- Demo has no real auth: a role switcher (Submitter / AP Reviewer / Admin).
- 2-way match by default; GRN quantity check when a GRN exists.
- Tolerance: unit price must exceed both 2% and $50 per unit to fail; PO balance tolerance 2%.
- Implied PO matches never auto-approve.
- Seeded dashboard history is labelled as seeded demo data in the UI.

## Phase B1
- Case status enum adds `unsupported`: workflow.yaml ends at `end:unsupported` (no invoice found) but SPEC §6 omitted it. Allowed terminal targets: approved, rejected, unsupported, failed.
- `workflow.yaml options.sticky_review_redirect: {auto_approve: template_draft}` names where sticky review sends an auto-approve once a reviewer has acted, so the stage id is not hard-coded. "Has been reviewed" = at least one review_action row exists.
- Pause statuses: a `hitl` stage sets the case to `needs_review`; a `wait_for` stage sets it to `on_hold` (with `sla_due_at` from `app.sla_hours`).
- Each case runs on the config snapshot taken at creation (hash + full files in `cases.config_snapshot`); later Agent Studio edits apply to new cases (and to reruns, once rerun exists).
- Case state is not a column: it is folded from completed/waiting stage_event outputs per agent id (append-only, replayable).
- `run_no` increments on every resume (review action, event, startup restart); stage_events `seq` is per case.
- Added `cases.note` (upload form note; not in SPEC §6) and `app.yaml limits.max_stages_per_run` (loop guard).
- Agents whose handler module does not exist yet run as `StubAgent`; `FORCE_STUB_AGENTS=true` forces stubs everywhere. Tests always force stubs and script outcomes per stage (`!error` / `!sleep:s` to test retries and timeouts).
- Sync SQLAlchemy sessions are used inside async routes and the orchestrator (queries are tiny; concurrency is 2). Revisit if Postgres latency on Render shows up in the live view.
- `make check` skips the frontend typecheck/build while `frontend/package.json` does not exist (F1 creates it); it uses make's `$(wildcard)` so it is shell-agnostic.
- SSE: `GET /api/cases/{id}/events/stream` replays stored events (honours `Last-Event-ID`), then streams live `stage_event`, `case_updated` and `progress` events; `?follow=false` closes after the replay.
- Accepting a review action or a `wait_for` event writes the paused stage's `completed` event and moves `current_stage` to the next target before the job is queued, so a restart (Render sleeps often) continues from there instead of losing the action.
- An orchestrator-level crash (loop guard, DB error) still appends a `failed` stage_event with the error text.
- Deferred: a review POST that arrives while the same case is mid-run waits for the per-case lock before getting its 409. That's harmless with stubs; revisit in B2 when LLM stages take seconds.

## Phase B2
- Bundles: the classifier gains outcome `split` -> `end:split` (new terminal case status `split`; F-phases need a colour for it in `status.ts`). Each invoice in the upload becomes a child case (`parent_case_id`, same submitter, source and config snapshot) and is queued by the orchestrator through the new `AgentResult.spawn` list. A child's document row points at the parent's stored file with `page_from`/`page_to` and the label already set, so the child skips the classifier LLM call (FakeLLM `when.pages` keys on original page numbers, and bbox pages stay those of the original file). The same rule applies to any upload with more than one invoice, including several single-invoice files.
- One file holding several documents (e.g. an invoice plus a delivery note) keeps one `documents` row per page-range segment (same `storage_key`, no bytes copied).
- Page renders and text layers are content-addressed in storage: `renders/<sha256>/pages/<n>.png` and `renders/<sha256>/text.json`, so segments and child cases share them. The future `/documents/{doc_id}/pages/{n}.png` route resolves via `documents.sha256`.
- Intake: a file whose format is not PDF, image or DOCX is skipped with a reasoning line; if nothing usable is left the outcome is `empty`. More pages than the limit is `too_large`. DOCX is converted text-only (PyMuPDF cannot open DOCX, and there is no LibreOffice on Render free). "Scanned" means fewer than `intake.params.min_text_chars` characters in the text layer.
- Classifier: the label enum is injected into the strict schema from document_types.yaml. A label below `min_confidence` becomes `other` (the model's label and confidence stay in the reasoning). Images of the first `pages_per_document` pages plus the text layer of every page (truncated to `max_text_chars`) are sent, so a long bundle is still split correctly.
- Extraction: the outcome is `failed` only when there is no invoice number, no total and no lines; it is `low_confidence` when any configured `confidence_fields` value is below `low_confidence_below`. `cases.confidence` = the minimum of those header confidences. Exact bboxes: each located value is searched in the text layer (amounts with and without thousands separators; ISO dates re-printed in `locate_date_formats`). Among several hits, the one closest to the model's box wins. Values that wrap across lines (e.g. a two-line vendor name) fall back to the model's box, marked `source: model`.
- Vendor memory before the vendor check: the vendor is "known" from the vendor stage (a re-extraction), else the submitter's email domain, else a master legal name printed in the text layer.
- Normaliser: amounts are emitted as decimal strings (exact in JSON). Its output (`state.normaliser.invoice`) is the canonical invoice for B3; `extractions` keeps the model's raw output. Missing line amounts are computed from qty x unit price, and a subtotal+tax+shipping vs total mismatch becomes a warning plus `arithmetic_ok: false` (the rule decides in B3). Ambiguous numeric dates follow `date_formats_hint` order and are flagged.
- LLM adapter: `api_path: auto` is resolved by a background probe at startup (a tiny strict-schema Responses call, then a Chat call); `/healthz` shows `responses|chat|unavailable|not_probed`. The strict-schema post-processor also drops `minimum/maximum/format/default/title` and rewrites `const` to `enum` (Pydantic validates bounds after parsing). Cached responses report 0 tokens and cost with `cache_hit: true`. An agent YAML without `model.max_output_tokens` is an error, not a silent default.
- `LLM_BACKEND=fake` serves the recorded FakeLLM fixtures from the running app (frontend work offline); default is `azure`.
- Fixed B1's deferred item: a review POST on a case that is not `needs_review` now returns 409 at once instead of waiting for the per-case lock while an LLM stage runs.
- Live run (gpt-5.2, Responses path): header-field accuracy 36/36 on S01, S04, S08, S09. Extraction takes 25-41 s per call at medium effort; classification takes 3-10 s. Cost shows $0 until `llm.pricing_per_1m_usd` in app.yaml is filled in.
- `make test-live -k extraction` would hand `-k` to make (keep-going), so the Makefile passes `ARGS`: `make test-live ARGS="-k extraction -s"` prints the table.
- Spec review fixes: re-running the classifier on an already split bundle (a restart before the stage event was written) reuses the existing child cases and queues nothing new. One-word values are located only as whole words (`$100.00` is matched, but `100.00` is not found inside `1,100.00`, nor `8.25` inside `8.25%`). Numeric date formats moved to `normaliser.params.date_numeric_formats`.
- Deferred from the B2 review:
  - A real invoice the classifier labels below `min_confidence` becomes `other`, so the case ends `unsupported` with the reason in the reasoning lines. A "low-confidence document → review" route needs a workflow outcome and a UI state; revisit in P6 if live classification ever drops below 0.70 (live runs were 0.95+). *Superseded: see "Backend fixes before F2".*
  - Pages no classified range covers are dropped without a reasoning line. *Superseded: they now get one.*
  - `normaliser.arithmetic_ok` is an exact cent check for display only; B3 rules must apply the rules.yaml tolerance.

## Phase B3
- Duplicate detection needs the invoice number per case, so `cases` gains `invoice_number` (as printed), `invoice_number_norm` (indexed) and `invoice_date`, set by the normaliser and exposed on `CaseOut`. No Alembic: run `make seed` to recreate a dev DB.
- Duplicate candidates are other cases of the same vendor that are not seeded and not `failed/unsupported/split/rejected`. `duplicate_near` compares invoice dates (else created dates) within `window_days`; an invoice with no number counts as a different number (S09 is flagged as a possible duplicate of S10's CL-781: same vendor, same 1,250.00, no number).
- Rule scope: `applies_to: po` rules run when a PO is linked **or** a PO number is printed (so `po_valid` can explain a bad reference); rules that need PO data (price, GRN, balance, lines, currency) are then "not applicable" without a linked PO. `non_po` rules run when no PO is linked. Not-applicable rules are listed in the policy output (`not_applicable`), not stored as rule_results.
- Rule statuses: `fail`; `warn` for an info-severity failure or a reviewer override (explanation "Overridden by reviewer: <reason> (was: …)"); `pass` (explanation "<rule name>: OK."). Multi-item rules (price, GRN) render `explain` once per offending line and join them.
- Boundaries are strict "greater than": exactly at a tolerance passes. `price_tolerance` only flags over-billing. `po_balance` compares the invoice **subtotal** (pre-tax, as the S02b numbers require) with remaining = (PO amount, or the reviewer's amendment for this case) - reserved/consumed by other cases; with nothing left any amount fails ("over by 100+%"). `quantity_vs_grn` compares with GRN received minus qty already invoiced against that PO line by other cases, and only for PO lines that have a GRN. `tax_rate_valid` uses printed line rates when present, else accepts any allowed rate within `rounding_tolerance` (new param, 0.01) of tax_total.
- Date rules use today's date via `app.agents.policy.today()` (tests pin it to 2026-10-11).
- Reconciler contract for B4: policy reads `state.reconciler.rule_overrides {rule_id: reason}` and `state.reconciler.po_amendments {po_number: amount}`.
- Decision outcomes come from `decision.yaml params` (`severity_outcomes`, `pass_outcome`, `gate_failure_outcome`). The `min_extraction_confidence` gate checks the `required_fields` rule's fields; a missing confidence fails the gate. `require_explicit_po` means non-PO and implied invoices never auto-approve.
- Reservation: at `decide`, for outcomes in `reserve_po_balance_on`, the case's earlier reservation is released and one row per invoice line is reserved (lines not on the PO count against the PO header). Right before reserving, `po_balance` is re-run against the live ledger with no `await` in between; if it now fails, an auto-approve becomes needs_review. On hold / reject release the case's reservation. Consumption on approval (`po_ledger.consume`) is called by `finalize` in B4, so after B3 S01 shows PO-1002 4,415.00 *reserved*, not yet consumed.
- The decision explanation LLM call gets only the rule results and gate failures; if it fails, the summary is built from the failing rules' explanations (reasoning line says so) and the stage still completes.
- Vendor check: `pending_docs` vendors route to `new_vendor` (onboarding reuses the open request); `inactive`/`rejected` to `inactive_vendor`. IBANs are compared as sha256 of the upper-case alphanumeric IBAN. `request_onboarding` creates the vendor row (`pending_docs`, next `Vnnn` code, details from the invoice) plus a vendor_request with a random token; the output carries `portal_path` `/portal/<token>`, and comms/UI prefix `PUBLIC_APP_URL`.
- PO inference: amount closeness = 1 - |subtotal - remaining| / max(both); date score = 1 when the invoice is dated 0..`date_window_days` after the PO, else 0; line similarity from the LLM. For an explicit PO the LLM is still called once (one candidate) for line pairing. Model-proposed pairs are validated in code (PO line must exist, used once). An explicit reference that is missing/closed/another vendor's is recorded as `explicit_issue` and the vendor's open POs are scored instead.
- suggest_gl only accepts codes from `gl_accounts`; unknown suggestions fall back to the vendor's default GL (noted in reasoning). History = the primary GL of the vendor's last 5 approved non-PO cases.
- Scenario test asserts `failed_rules` as a subset (as D1 noted); S05's `after_onboarding` simulates the admin approval directly (vendor status + `fire_event(vendor_approved)`) until B4 builds the portal/approve endpoints.
- Spec-review fixes: a late `po_balance` failure at reservation time also rewrites that rule's stored result and feeds the explanation, so the Rules tab and the summary agree with the decision. The reservation equals the subtotal that `po_balance` checks (a gap between the subtotal and the line amounts is reserved on the PO header). Duplicate candidates are only *earlier* cases, so two copies processed concurrently don't reject each other. Model-proposed line pairs also need a rapidfuzz description floor (`po_matching.params.pair_min_similarity`, 50). Severity ordering in reasoning follows `decision_precedence`; the GL history size is `gl_history_cases`.
- Deferred to B4: (1) a case that fails after `decide` (e.g. at the template stage) keeps its reservation; B4 should release it on `end:failed` / rejection along with `consume` on finalize. (2) `po_ledger.balance()` (PO screen) shows the master amount; a reviewer's per-case `po_amendments` raises the amount only for that case's rule, so the PO screen can show a negative remaining (PO-1001 -300.00 after S02b until the amendment is applied in B4). *(2) superseded: see "Backend fixes before F2".*

## Phase B4
- Reviewer changes never edit other agents' outputs (stage events stay append-only). The reconciler stores its validated effects under its own state key (`invoice` with field edits, `po_matching` after link/unlink, `gl_overrides`, `rule_overrides`, `po_amendments`), cumulative across remarks; `app/case_state.effective()` overlays them for policy, decision, template and exports. GL per line = reviewer override > PO line GL > suggest_gl > vendor default.
- Reconciler validation is all-or-nothing: an op not in `allowed_ops`, a rule in `non_overridable_rules`, an unknown rule/GL/line/field path, a PO that is not the vendor's (link_po) or not the linked one (set_po_amount_note), or any `ask` returns `needs_clarification` with the reasons as the question; nothing is written except the ChangeSet on the remark row. `override_rule` and `set_po_amount_note` are logged as `review_actions` rows (`action=override`, the reviewer as actor, the reason as text). A reviewer-linked PO counts as `explicit` (`linked_by: reviewer`). link_po pairs lines in code (rapidfuzz best match, then the usual validation); no LLM call.
- `set_po_amount_note` raises the PO amount for that case only (SPEC §7). After S02b is approved, PO-1001 shows consumed 10,300 of 10,000 (remaining -300) on the PO screen: the master amount is not changed by a remark. The F3 PO screen should show the amendment from the case's override log. *Superseded: approval now amends the master amount (see "Backend fixes before F2").*
- Vendor memory is written for `add_vendor_memory` hints and for every reviewer `set_field` edit ("Reviewer corrected <path> from X to Y on <ref>"), when `features.vendor_memory` is on and the vendor is known.
- Template: the profile comes from `template.params.erp_profile` (fallback `app.default_erp_profile`); per-case profile switching is not built. Missing required cells are reported (`missing`, reasoning line) but `generate_draft` still returns `ok` (its only outcome); the reviewer sees the gap. `money` prints plain 2-dp numbers (no thousands separator) because import files expect that. `created_by=reviewer` for a version rendered after a reconciler change.
- Finalize stamps `cases.approved_by` (the last approving reviewer, else `auto`) and `approved_at`, re-renders, and freezes the latest version (a new final version only if stamping changed a cell, e.g. generic_xlsx "Approved By"). It writes the file to storage and consumes the PO reservation. The case status becomes `approved` at `end:approved` (one stage later, after notify), not inside finalize. New columns: `cases.approved_by/approved_at/exported_at`; `vendor_requests.case_id/kind (onboarding|info)/checks/message`. Run `make seed` to recreate a dev DB.
- Reservations are released when a case ends `rejected` or `failed` (orchestrator, generic). That closes B3's deferred item 1.
- Comms: what a hold request asks for is config (`comms.params.request_needs` per failed rule, `need_text`, `missing_fields_suffix`); notification texts are config too. A hold opens (or reuses) one `info` vendor_request per case so the portal can resume it; onboarding reuses the vendor agent's request. The portal link is appended to the LLM body when the model leaves it out. If the LLM call fails, a plain deterministic draft is used so the case still pauses with a message (rejections for scenarios without a comms fixture use it under FakeLLM).
- Portal: upload -> store + render -> the classifier agent's `classify_document` (same prompt and label enum) -> code checks: vendor name in the text (rapidfuzz partial_ratio >= `vendor.params.document_name_min_score`, 85), tax ID present and in the country format, bank account digits present. Scans without a text layer get a `manual` check. When every needed document is in: requests needing a tax form or bank letter become `submitted` and wait for an admin (`POST /api/vendors/{id}/approve`); a request that only needs a corrected invoice resumes the case immediately. Resuming fires the paused stage's own `wait_for` event (read from workflow.yaml), so event names are not hard-coded. Extraction prefers a corrected invoice uploaded after the classifier's choice.
- Approving a vendor also applies a verified bank change: for an `info` request whose received docs include `bank_letter`, the case invoice's account last 4 / IBAN hash replace the master's (noted in the response). Rejecting a vendor marks its open requests rejected; waiting cases stay on hold (no automatic case rejection).
- Exports: `POST /api/exports {case_ids, erp_profile, mode: zip|batch, force}`. Only `approved`/`exported` cases; any already-exported case -> 409 unless `force`. Batch = the profile's `batch.filename_template`, rows concatenated in the order given, header once (`mode: concat_rows` is the only batch mode). Rows come from the frozen final version when it used the same profile; otherwise the case data is re-rendered with the requested profile. Export refs and the ZIP file name come from a new `app.yaml exports` section. Exported cases move to status `exported` with `exported_at`.
- Added endpoints the later F phases need: `GET /api/cases/{id}/documents/{doc}/file|pages/{n}.png`, `GET /api/vendors[/{id}]`, `GET /api/pos[/{id}]`, `GET /api/notifications`, `POST /api/notifications/{id}/read`.
- Spec-review fixes: (1) approving a vendor resumes only the cases its requests paused (an `info` request only once its documents were submitted), plus other invoices of that vendor waiting on the same onboarding event. Invoices held for other reasons stay paused. (2) Reviewer overlays carry `based_on_seq` (the normaliser event they edited). After a re-extraction (corrected invoice via the portal) they are dropped, including GL overrides, rule waivers and PO amendments. The reviewer then reviews the new invoice. (3) `set_po_amount_note.new_amount` must appear as a number in the remark text, else `needs_clarification`: a money figure is never taken from the model alone. (4) A bank change applied at vendor approval writes an `override` review_action (admin, old/new last 4, failed checks). (5) The documents that wait for an admin are `vendor.params.admin_verified_docs`. (6) Export refuses (422) rows with an empty `required` column.
- Deferred from the B4 review:
  - Typed reviewer edits (`ReviewIn.ops`, inline grid edits as `set_field` without the LLM) go in F2, when the review grid exists. Today field edits go through remark text.
  - `set_field` on `remit_bank.*` / `vendor_tax_id` is allowed. A bank failure routes to hold, not review, so a remark can't reach it today. A config denylist can come if that routing changes.
  - The `EXP-nnnn` ref is count-based. Two exports in the same instant could collide on the unique ref (500); acceptable for a single-reviewer demo.

## Phase F1
- Backend endpoints the graded screens needed (SPEC §9 named some, nobody had built them): `GET /api/dashboard/metrics?range=` (`app/dashboard.py`), `GET /api/cases/{id}/journey` (`app/journey.py`), `POST /api/cases/{id}/rerun {from_stage}` (the live view's Retry), an `after=<seq>` query on the SSE stream (a manual reconnect cannot set `Last-Event-ID`), a `submitter_email` filter on `GET /api/cases`, and `vendor_name` on `CaseOut`.
- UI config lives in a new `app.yaml ui` section, validated by `config_loader.validate_ui`: `journey` (courier steps -> workflow stage ids / case statuses), `stage_chips` (per-agent chip templates `{path|money|pct|count}` rendered on live-run cards; a chip with a missing value is hidden), `status_text` (journey headline per case status, `{label}` / `{needs}`), `dashboard` (ranges, default range, recent rows, which decisions count as "exceptions caught", the decision stage), `cold_start_after_ms`. Stage order, labels and agent names in the UI come from `/api/config`, never from TSX constants.
- Dashboard KPI definitions: cases = created in the range, bundle parents (`split`) excluded; straight-through = decided cases with `auto_approve`, no review action, status approved/exported; in review / on hold = live counts (not range-bound); time to decision = median of (first completion of `ui.dashboard.decision_stage` - case created); exceptions caught = sum of totals of decided cases whose decision is in `exception_decisions`; exceptions by rule = distinct cases failing each rule in their latest policy run; LLM cost per invoice = sum of `metrics.cost_usd` / cases. Seeded history is counted and labelled ("N seeded demo cases") rather than hidden.
- Rerun is allowed for `failed`, `needs_review` and `on_hold` cases (default start = the stage it failed or paused at); approved, exported, rejected and split cases are final (409), as is a running case.
- Journey "waiting for" text comes from the hold draft's new `needs_text` (comms `need_text`), so the submitter sees the same words the vendor email uses.
- `FAKE_LLM_DELAY_S` (dev only) slows FakeLLM calls so an offline run can be watched and screenshotted mid-run; `scripts/dump_openapi.py` + `npm run gen:api` regenerate `frontend/src/api/schema.ts` without a running server (generated file committed so the Vercel build needs no backend).
- Frontend: Tailwind 3 + hand-written shadcn-style components (Radix primitives) instead of the shadcn CLI (it is interactive). Role and theme are per-viewer `localStorage` preferences; the role only filters navigation (no auth, as assumed). Saved table views are also per-browser.
- Screens that belong to F2/F3 (review workspace, approved library, vendors, POs, Agent Studio) are routed to a "arrives in phase F2/F3" placeholder. The scenario launcher is built minimally here because the F1 done-check runs S01 from it; F3 extends it.
- Known FakeLLM artefact, not a UI bug: the decision explanation fixture is keyed by document, so re-running S01 (a duplicate -> reject) shows the S01 "Auto-approved…" summary text next to a Reject badge. ## Backend fixes before F2
- Event loop: the orchestrator (workers, job queue, per-case locks, every agent run, and so all pipeline DB and LLM calls) runs on its own event loop in a background thread named `orchestrator`. `submit_review` / `fire_event` / `rerun` / `resume_pending` / `join` hop onto it with `run_coroutine_threadsafe`. `enqueue` and the `EventBus` are thread-safe (each SSE queue is fed on the loop that subscribed). API routes that only touch the DB are plain `def` (FastAPI's threadpool); the async ones (`create`, the SSE stream, review, rerun) wrap their DB work in `run_in_threadpool`. Portal uploads and vendor approval run on the orchestrator loop through `orch.call()`, as does the Azure startup probe (`orch.submit`), so the AsyncOpenAI client is only ever used from one loop. A slow DB call in the pipeline therefore never stalls SSE (`tests/test_concurrency.py` runs uvicorn with 0.8 s stage_event inserts and checks that healthz stays under 0.4 s and events stream as they happen).
- Low-confidence classification: when no document is a confident invoice but the model labelled one `invoice`/`credit_note` below `min_confidence`, the classifier returns the new outcome `low_confidence` (workflow: -> `extract`). It keeps the model's label on that document and records `uncertain_invoice`. The new rule `document_classification` (severity review) then fails, so the case ends in `needs_review` with "The classifier was only 55% sure ... is an invoice" instead of `unsupported`. An uncertain non-invoice label (e.g. a 50% statement) still ends `unsupported`. If extraction then finds nothing at all, the case ends `failed` as for any unreadable invoice.
- Pages no classified range covers get a reasoning line ("page(s) 2 matched no document type and were left out").
- Arithmetic `abs_tolerance` was already in the engine and boundary-tested (`test_arithmetic_boundary`); no change.
- Master data CSV: `GET /api/master/{vendors|purchase_orders|po_lines}.csv` and `POST /api/master/{entity}/import` (multipart `file`, `actor`). The format is the data/master contract the seed reads (columns listed once in `app/master_csv.py`, not config, since they map 1:1 to model fields). Import is an all-or-nothing upsert (422 with every row error). An existing vendor's `bank_last4`/`iban_hash` cannot change by import: bank details change only through a verified bank letter. A changed PO amount goes through `po_ledger.amend` (audit row, `source=import`).
- `set_po_amount_note` (supersedes the B4 "this case only" note and SPEC §7's wording, at the user's request): the amendment still applies to the case's own rules as soon as the remark is applied. When the case is approved (`template.finalize`), it also becomes the PO's master amount, with a `po_amendments` row (`amended_by` = the reviewer who wrote the remark, old/new amount, reason, case_id, `source=remark`). This mirrors the verified bank change on vendor approval. S02b: PO-1001 = 10,500, consumed 10,300, remaining 200. `GET /api/pos/{id}` returns `amendments`.
- Decision summary: the first sentence is built in code from the final rule results (`decision.params.decision_labels`): "<label>: <fail_label of the highest-precedence failed rule> (and N other failed checks)." It falls back to the first failed auto-approve gate, else "every check passed". The LLM is given that sentence and writes only the detail and next step. If its text uses another decision's phrases (`decision.params.decision_terms`), it is discarded and the failed rules' explanations are used instead. A detail that restates the same decision label is trimmed. So the summary can never contradict the decision (S04 run twice: the first is needs_review although the only S04 fixture text says "Rejected: duplicate"; the second is rejected).

## Phase F2
- Typed grid edits (the item B4 deferred): `POST /api/cases/{id}/review` takes `ops` with `action=remark`, and only `set_field` / `set_gl` ops (schema-enforced; `ops` with another action is 422). They are stored on the remark row (`changeset {source: grid, ops, status: pending}`), and the reconciler applies them **without an LLM call** through the same all-or-nothing validation as a written remark. Waivers, PO amendments and PO links still need a written remark (the model proposes them, code validates them, and an amount must appear in the text). The text is optional when `ops` are sent; the reviewer can add a note. A written remark plus grid edits in one submit: the edits are applied exactly and the note is kept in the audit trail. It is not sent to the model.
- `GET /api/cases/{id}/workspace` (`app/workspace.py`) gives the HITL screen what the case detail does not have. (1) Template columns with their bindings and edit spec, derived from each ERP profile column's Jinja value: a cell is editable only when its template is a single `inv.<field>` / `line.<field>` expression the reconciler accepts (`reconciler.edit_input`), and `line.gl_code` / `line.department` become `set_gl`. Column names are never hard-coded in TSX. (2) Amber cells. (3) The effective invoice, so edits start from raw values (ISO dates, plain decimals) rather than the profile's formatted text. (4) The PO match lines with GRN qty. (5) The PO balance, computed live from the ledger (others' reserved + consumed, the reviewer's amendment, this invoice's subtotal as `po_balance` uses). (6) The latest comms draft. (7) Duplicate links: any failed rule whose evidence has `other_case_id`.
- Amber cells: a failed rule marks the cells listed in its new optional `highlight` (rules.yaml): invoice fields, `lines.<field>` (only on the lines named by the evidence's `line_indexes` / `items[].line_index`, else every line), `po`, `vendor`, or `evidence:<key>` (field names listed in the evidence, e.g. required_fields' `missing`). Low confidence uses the new `app.yaml ui.review.low_confidence_below` (0.90, the auto-approve gate's level). A field the reviewer has since edited is not flagged for low confidence. Waived (`warn`) rules don't mark cells. `po_balance` highlights `po` + `subtotal` (a header-level check), not every line amount.
- PDF highlights use the extraction's `field_meta` boxes (page + normalised bbox) on the document the extraction stage read. Hovering a grid cell bound to a header field highlights its box, and hovering a box highlights the cell(s). Line items have no per-line boxes (the extraction schema locates fields, not lines), so line cells don't link to the PDF. react-pdf renders the stored file with text and annotation layers off. If pdf.js can't open it, the intake page PNGs are shown instead.
- Columns that are empty on every row and are not required, flagged, changed or being edited (e.g. Sage's `DONOTIMPORT`, an unused `DEPARTMENT_ID`) are hidden behind "Show N empty columns". The grid scrolls the first changed or flagged cell into view, and a strip above it lists every v(n) cell change, so the diff is visible without scrolling.
- Approve (A) asks for confirmation (Enter confirms): a single key press must not finalise a payable. It is blocked while grid edits are unapplied. Reject (X) requires a reason. Request changes (R) sends the remark and/or grid edits. Ask vendor (V) sends `request_info` with the reviewer's text, then shows the comms draft in the same modal (Copy, Open in mail app = the `mailto:` link, Copy upload link, Open portal). On a held case, V reopens the draft. Shortcuts are ignored while typing in a field or when a dialog is open.
- The comms plain fallback draft (used when the model call fails, and under FakeLLM for scenarios without a comms fixture) now lists the reviewer's own request first. Before, it only listed the rule-derived needs, so "Ask vendor" could send a message that didn't contain what the reviewer asked for.
- Duplicate compare: a case with a duplicate link opens in compare view (the toggle is in the header, `?view=review` to leave it): the rule's explanation, a field-by-field table (matching values highlighted; invoice numbers compared ignoring case/spaces/punctuation, display only), and both invoices' PDFs side by side.
- After a remark the page polls the case while it reruns. When the reconciler asks for clarification, a toast shows the question and the History tab opens. When it succeeds, the toast names the new template version. A case whose rules now pass but that is back in review because of `sticky_review` gets a one-line explanation under the decision.
- The actor on review actions is the role label from the role switcher ("AP Reviewer" / "Admin"): there is no auth (SPEC §13).
- Evidence: `docs/screenshots/f2/` (light and dark), produced by `node frontend/scripts/review-screenshots.mjs <dir> <theme>` against a freshly seeded API (`LLM_BACKEND=fake`).
